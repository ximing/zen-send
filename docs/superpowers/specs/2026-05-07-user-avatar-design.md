# User Avatar & Nickname Feature Design

## Overview

Add user avatar and nickname support across web, mobile, and server. Users can view and edit their avatar and nickname in the settings page. Avatar upload uses S3 presigned URL direct upload, reusing the existing S3 infrastructure.

## Data Layer

### Database Schema Changes

Add two nullable columns to `users` table (`apps/server/src/db/schema.ts`):

- `avatarKey: varchar('avatarKey', { length: 500 })` — stores S3 object key (e.g. `avatars/{userId}/{timestamp}.{ext}`), not a URL. Named `avatarKey` (not `avatarUrl`) to match existing convention where `transferSessions.s3Key` stores S3 keys.
- `nickname: varchar('nickname', { length: 50 })` — nullable, client falls back to email prefix when not set

Both fields nullable, no impact on existing data. Migration generated via Drizzle. Profile updates must set `updatedAt` to current Unix timestamp.

### DTO Changes (`packages/dto/src/index.ts`)

New types:

- `UpdateProfileRequest` — `{ nickname?: string, removeAvatar?: boolean }`. Avatar updates are separate from nickname because the two-phase presign upload flow requires distinct endpoints. `removeAvatar` allows deleting avatar without uploading a new one.
- `AvatarPresignRequest` — `{ contentType: string, fileSize?: number }`
- `AvatarPresignResponse` — `{ uploadUrl: string, key: string }`
- `AvatarConfirmRequest` — `{ key: string }`
- `UserProfileResponse` — `{ id: string, email: string, nickname?: string, avatarUrl?: string }`

Note: `UserProfileResponse.avatarUrl` is a fully resolved presigned download URL generated by the server from the stored `avatarKey`, not the raw S3 key. Clients can use it directly as `<img src>`.

### Shared Types (`packages/shared/src/index.ts`)

Update `AuthTokens.user` to include `nickname?: string` and `avatarUrl?: string`. The `avatarUrl` is a presigned download URL resolved at login time. Since presigned URLs expire and the value can become stale, clients should refresh profile data via `GET /api/users/me` when needed (e.g. on settings page load). JWT payload stays minimal — only `userId` and `deviceId`.

Server-local `AuthTokens` interface (`apps/server/src/services/auth.service.ts`) must also be updated to include `nickname` and `avatarUrl`, or better — import from `@zen-send/shared` instead of redefining.

## API Layer

### New UserController (`apps/server/src/controllers/user.controller.ts`)

Uses `@JsonController("/users")` with `@Authorized()` decorator. Services injected via constructor (typedi), following existing controller patterns. Register in `controllers/index.ts`.

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/api/users/me` | GET | Return current user profile (`UserProfileResponse`). Server resolves `avatarKey` → presigned inline URL for `avatarUrl` field. |
| `/api/users/me` | PATCH | Update profile (body: `UpdateProfileRequest`). Can update nickname or remove avatar. Sets `updatedAt`. |
| `/api/users/me/avatar/presign` | POST | Get presigned upload URL (body: `AvatarPresignRequest`). File size validation is best-effort pre-check (client-side 2MB limit is primary enforcement, as S3 presigned URLs cannot enforce upload size at S3 level). |
| `/api/users/me/avatar/confirm` | POST | Confirm upload, update avatarKey, delete old avatar from S3 (body: `AvatarConfirmRequest`). Sets `updatedAt`. |

### S3Service Changes

Add `getPresignedInlineUrl(key, expiresIn)` method to `S3Service`. Unlike existing `getPresignedDownloadUrl()` which sets `Content-Disposition: attachment`, this method returns a URL suitable for inline display (`Content-Disposition: inline` or omitted). Avatars displayed in `<img>` tags need inline URLs, not download URLs.

### Avatar Upload Flow

1. Client selects image → calls `POST /avatar/presign` with `contentType` and `fileSize`
2. Server validates contentType (only `image/jpeg`, `image/png`, `image/webp`) and fileSize (max 2MB as best-effort pre-check), generates key (`avatars/{userId}/{timestamp}.{ext}`), calls S3Service for presigned URL. The presigned URL is bound to the `Content-Type` header — if a client uploads with a different content type, S3 will reject it, which is an intentional security safeguard.
3. Client uploads image directly to S3 via presigned URL with matching `Content-Type` header
4. On upload failure: client can retry by requesting a new presigned URL. No server-side cleanup needed since unconfirmed keys are orphaned objects in S3 — acceptable for small avatar files.
5. Client calls `POST /avatar/confirm` with `key`
6. Server validates: key must start with `avatars/{currentUserId}/` (prevents path traversal / pointing to other users' objects) → updates `users.avatarKey` → deletes old avatar from S3 if exists

### Avatar Removal

`PATCH /api/users/me` with `{ removeAvatar: true }` sets `avatarKey` to null and deletes the old avatar from S3.

### Concurrency Handling

If two devices upload simultaneously, the last confirm wins and the loser's avatar is deleted from S3. This is acceptable for a single-user profile edit scenario. No row-level locking needed — the risk is minimal and the consequence (one avatar replaced by another) is expected behavior.

### Validator (`apps/server/src/validators/user.validator.ts`)

- `UpdateProfileRequest`: nickname optional (max 50 chars), removeAvatar optional (boolean)
- `AvatarPresignRequest`: contentType required, only `image/jpeg`, `image/png`, `image/webp`; fileSize optional, max 2097152 (2MB)
- `AvatarConfirmRequest`: key required

### UserService (`apps/server/src/services/user.service.ts`)

Decorated with `@Service()`, injected into `UserController` via constructor.

- `getProfile(userId)` — query user, resolve `avatarKey` to presigned inline URL via `S3Service.getPresignedInlineUrl()`
- `updateProfile(userId, data)` — update nickname and/or remove avatar, set `updatedAt`
- `presignAvatar(userId, contentType)` — validate type/size, generate presigned URL
- `confirmAvatar(userId, key)` — validate key prefix, update `avatarKey`, set `updatedAt`, delete old avatar from S3

### Auth Response Change

`AuthService.login/register` returns `AuthTokens.user` with `nickname` and `avatarUrl` (presigned inline URL resolved from `avatarKey`) fields added.

## Web Client

### Settings Page (`apps/web/src/pages/settings/index.tsx`)

Replace stub with full profile editing page. Uses page-level service binding: `bindServices(SettingsContent, [UserService])`.

- Avatar display: circular, shows image if avatarUrl set, otherwise first-letter placeholder
- "Change avatar" button → file input (`accept="image/jpeg,image/png,image/webp"`) → validate file size client-side (2MB max) → presign upload flow → confirm → update local state
- "Remove avatar" link (shown only when avatar exists) → `PATCH /api/users/me` with `removeAvatar: true` → update local state
- Nickname input: shows current nickname, editable, save button on right
- Save nickname → `PATCH /api/users/me` → update local state
- Page load: fetch `GET /api/users/me` for fresh profile data (handles presigned URL expiry)

### NavContent Update (`apps/web/src/components/nav-content/index.tsx`)

- Show avatar image when avatarUrl exists
- Show nickname when set, otherwise email prefix
- Click avatar area → navigate to settings page

### New Service

`apps/web/src/services/user.service.ts` — `@Service()` class with API calls for getProfile, updateProfile, presignAvatar, confirmAvatar. Page-level service, not globally registered.

### Auth State

`AuthService` user type adds `nickname?: string` and `avatarUrl?: string`
